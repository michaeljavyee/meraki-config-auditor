critical DRIFT-001 VLAN / 802.1Q trunk

VLAN 40 (cameras) is in use on 5 access ports but is not carried on the switch's uplink trunk. Those ports have no path off the switch.

Depot-West / SW-WEST-IDF1 port 8
Evidence

SW-WEST-IDF1 (Q2XX-WE00-SW03) uplink port 8 'Uplink': type=trunk, allowedVlans='1,10,20,30'. Missing from the allowed list but assigned locally - VLAN 40: access ports 1, 2, 3, 4, 5.

Business risk

Every device on those 5 ports is offline right now. They still have link and PoE, and the switch reports healthy in Dashboard, so nothing alerts: the failure is only visible from the device's side. This is the classic post-cutover outage - an uplink trunk rebuilt by hand with one VLAN left off - and it is typically discovered days later by someone who needed the device.

Remediation

Dashboard > Switching > Switch ports > SW-WEST-IDF1 port 8 > Allowed VLANs: add 40, then confirm the far end of the link allows it too. Afterwards, add the baseline's required VLAN list to the cutover checklist and run this audit before closing any switch replacement change.

high DRIFT-002 VLAN / 802.1Q trunk

Native VLAN mismatch across one link: SW-EAST-CORE port 23 uses native VLAN 1, SW-EAST-IDF1 port 8 uses 10.

Depot-East / SW-EAST-CORE:23 <-> SW-EAST-IDF1:8
Evidence

Link-layer topology pairs SW-EAST-CORE (Q2XX-EA00-SW01) port 23 with SW-EAST-IDF1 (Q2XX-EA00-SW02) port 8. Native VLAN: SW-EAST-CORE=1, SW-EAST-IDF1=10.

Business risk

Untagged frames leave one switch in one VLAN and arrive at the other in a different one. Anything that relies on the native VLAN - management traffic, devices on untagged ports downstream - ends up in the wrong segment. Besides intermittent connectivity problems that are very hard to diagnose, it is a segmentation leak: traffic crosses between VLANs without going through the firewall.

Remediation

Pick the standard native VLAN (1) and set it on both SW-EAST-CORE port 23 and SW-EAST-IDF1 port 8 in the same change window. Changing one end alone moves the problem rather than fixing it.

high DRIFT-003 L3 firewall policy

A non-standard allow rule above the baseline overrides 'Guest cannot reach internal', so the baseline rule never takes effect.

Depot-West / L3 outbound rules
Evidence

Rule #1: ALLOW any VLAN(30).*:Any -> Any:Any (comment: 'TEMP vendor access during cutover - remove after'). It matches all traffic that the later baseline rule 'Guest cannot reach internal' matches, and the MX stops evaluating at the first match.

Business risk

This is the most dangerous kind of firewall drift because it is invisible in review: the baseline rule is still there, correctly written, and anyone checking for it will find it. It simply never runs. Temporary rules added during migrations are the usual cause, and they are rarely removed.

Remediation

Confirm with the change owner whether the rule is still needed. If not, delete it. If it is, narrow it to the specific source, destination and port required and move it below the baseline rule it overrides: Dashboard -> Security & SD-WAN > Firewall > Outbound rules.

high DRIFT-004 Wireless SSID

Enabled SSID 'CVL-Install' is not part of the standard and requires no authentication.

Depot-West / SSID 'CVL-Install'
Evidence

SSID #2 'CVL-Install': enabled=true, authMode='open', bridged into VLAN 10 (corp), visible=False.

Business risk

Anyone within range can join this network without credentials and lands directly in VLAN 10 (corp). Hiding the SSID (visible=false) does not prevent this; the name is broadcast in probe responses. Installer and test SSIDs like this are routinely left enabled after the work is finished.

Remediation

If 'CVL-Install' is no longer needed, disable it: Dashboard > Wireless > SSIDs. If it is, add it to the baseline with an owner and move it off open authentication.

medium DRIFT-005 L3 firewall policy

Allow rule not in the standard, from any source to any destination on port 161.

Depot-East / L3 outbound rules
Evidence

Rule #1: ALLOW udp Any:Any -> Any:161 (comment: 'SNMP for monitoring vendor').

Business risk

Every rule outside the standard is a decision nobody re-reviews. Broad allows are how one site ends up materially more exposed than the others while still appearing to follow the same policy.

Remediation

Either adopt it into the baseline with an owner and a reason, or remove it. If it must stay, narrow source and destination to the specific hosts involved: Dashboard > Security & SD-WAN > Firewall > Outbound rules.

medium DRIFT-006 Wireless SSID

SSID 'CVL-Guest' differs from the standard in wpaEncryptionMode.

Depot-East / SSID 'CVL-Guest'
Evidence

SSID #1 on Depot-East. wpaEncryptionMode: expected 'WPA2 only', found 'WPA1 and WPA2'.

Business risk

The wireless link here is weaker than the standard. Allowing older encryption modes for compatibility keeps them available to everyone, including attackers who can force a downgrade.

Remediation

Dashboard > Wireless > Access control > SSID 'CVL-Guest': set wpaEncryptionMode to 'WPA2 only'. Change authentication and VLAN settings in a maintenance window; clients will reassociate.

medium DRIFT-007 Firmware

Firmware is a different major version (switch-16-8-1, target switch-17-1-4).

Depot-West / SW-WEST-IDF1
Evidence

SW-WEST-IDF1 (MS130-8P, Q2XX-WE00-SW03) runs 'switch-16-8-1'. Baseline target for switch: 'switch-17-1-4'. Switch versions in Depot-West: switch-16-8-1, switch-17-1-4. Device tags: replaced-2026-09.

Business risk

Devices that should behave identically don't. Mixed firmware within one site produces the hardest kind of fault: a feature or default that works on one switch and not the next, with identical configuration on both. A replacement unit shipped on old firmware after a hardware swap is the usual cause.

Remediation

Schedule SW-WEST-IDF1 for 'switch-17-1-4': Dashboard > Organization > Firmware upgrades > select the device > Schedule upgrade. Add 'upgrade to baseline firmware' to the hardware-replacement checklist.

medium DRIFT-008 VLAN / 802.1Q trunk

Uplink trunk does not carry VLAN 40 (cameras), which the standard requires on every uplink.

HQ / SW-HQ-IDF1 port 24
Evidence

SW-HQ-IDF1 (Q2XX-HQ00-SW02) port 24 'Uplink SW-HQ-CORE': type=trunk, allowedVlans='1,10,20,30'. Baseline trunks.required_vlans = 1,10,20,30,40. No access port on this switch currently uses 40.

Business risk

Nothing is broken today, which is exactly why this survives. The first device anyone connects to this closet in VLAN 40 (cameras) will get link and PoE but no network, and the person installing it will reasonably assume the device is faulty. This is how a five-minute install becomes a truck roll.

Remediation

Dashboard > Switching > Switch ports > SW-HQ-IDF1 port 24 > Allowed VLANs: add 40. Make the same change on the far end of the link so both sides match.

Structural recommendations

  • Gate network changes on this comparison. Every finding above was detectable from configuration alone. Running the audit as the last step of a cutover or hardware swap, before the change is closed, turns a week-long silent outage into a five-minute fix.
  • Keep the standard in version control. The baseline used here is a reviewed YAML file. When the standard changes, the change is a pull request with a reason, and "when did we start requiring VLAN 40 on uplinks?" has an answer.
  • Tag uplinks in Dashboard. Port tags make intent machine-readable. An uplink tagged uplink can be checked automatically; one identified only by its cable label cannot.
  • Give temporary changes an expiry. "TEMP" rules and installer SSIDs persist because nothing forces anyone to remove them. A comment with a date and an owner, and a recurring audit that flags it, does.

5  ·  Methodology, scope and limitations

What was examined

  • Uplink trunk allowed-VLAN lists against VLANs in use on each switch's access ports
  • Uplink trunk allowed-VLAN lists against the baseline's required VLANs
  • Native VLAN agreement across both ends of each discovered link, and against the baseline
  • MX L3 outbound firewall rules against the baseline policy, including rule order and shadowing
  • SSID authentication, encryption, VLAN and radio settings against the baseline
  • Running firmware per device against the baseline target for its product type

What was not examined

  • Switch access-port configuration drift (port security, 802.1X, STP guard) - planned
  • Orphaned or unused configuration objects (policy objects, group policies) - planned
  • Inbound firewall rules, port forwarding, 1:1 NAT, L7 and content filtering
  • Site-to-site VPN, SD-WAN and routing configuration
  • Live traffic, client data, and anything requiring packet capture
  • Configuration outside Meraki Dashboard (ISP equipment, third-party switches)
  • Any change to configuration. This tool cannot write.

Access and method

Configuration was read through the Meraki Dashboard API using HTTP GET requests only. No create, update or delete operation exists anywhere in the tool's codebase, and its CI pipeline fails the build if one is added. No configuration was changed, no device was rebooted, and no traffic was generated on the audited networks. Findings are a comparison between live configuration and the baseline /home/claude/meraki-config-auditor/baselines/example.yaml (v2026.09).

Limitations

  • Drift is measured against the baseline, not against best practice. A network that matches a weak baseline will report clean. The baseline is included with this report so it can be reviewed on its own merits.
  • Uplinks are identified by port tag or name. An uplink that is neither tagged nor named as one is not assessed, and is listed below if trunk ports were seen without an identifiable uplink.
  • Firewall shadowing is computed structurally. CIDR containment is evaluated exactly; VLAN object references and FQDNs are compared by equality, so overlap between differently-expressed objects can be missed.
